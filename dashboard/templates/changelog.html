Updates & Changelog

v2.8.0 — Advanced Guardrails, Fail2Ban & DLP

25. Juli 2026
  • Erweiterte Rule-Engine: Die Guardrails unterstützen nun dynamische Aktionen (deny, silent, redirect, rewrite) sowie einen shadow-Modus zum gefahrlosen Testen neuer Filter.
  • Fail2Ban: Bei wiederholten Guardrail-Verstößen (10x in 5 Min) wird das Token temporär gesperrt. Entsperrung manuell via POST /admin/unban möglich. Events werden in der neuen SQLite Tabelle guardrail_events protokolliert.
  • DLP & Output-Filtern: Prompts und LLM-Outputs werden vor der Übertragung auf kritische Muster (Kreditkarten, SSN) geprüft und blockiert oder maskiert.
  • Simulator-Tool: Das neue CLI-Tool `guardrails_simulator.py` erlaubt es, historische Prompts offline durch die Filter zu jagen, um die Auswirkung von neuen Guardrails zu prüfen.

v2.7.0 — Admin-Audit-Log

24. Juli 2026
  • Audit-Trail: Jede /maintenance/*-Aktion (Stop-All, Ollama-Lock/-Unlock, Evict-Models, Force-Purge, Cleanup, Logging, Gaming-Override) landet jetzt in einer neuen admin_actions-Tabelle — Zeitstempel, Aktion, Quelle (admin vs. auto), auslösende IP, Detail.
  • Neuer Endpunkt: GET /admin/actions (Admin-Token nötig) liefert die letzten Einträge.
  • Dashboard: Neue Tabelle „📋 Admin-Audit-Log" unter Admin → Settings, zeigt die letzten 100 Aktionen inkl. Quelle.

v2.6.0 — Auto-Lock bei ComfyUI-Rendering & Maintenance-Auth

24. Juli 2026
  • Automatischer Ollama-Lock: Sobald ComfyUIs Queue nicht leer ist (etwas rendert oder wartet), sperrt der Proxy lokale Ollama-Modelle von selbst — analog zur bestehenden Gaming-Mode-Erkennung. Wird die Queue wieder leer, hebt sich ein automatisch gesetzter Lock von selbst wieder auf.
  • Manuell hat Vorrang: Ein per Dashboard/API gesetzter Lock wird vom Auto-Detector nicht angetastet, auch wenn die ComfyUI-Queue zwischendurch leer ist — erst ein manuelles Entsperren gibt ihn wieder frei.
  • Sicherheitsfix: Alle /maintenance/*-Endpunkte (Stop-All, Ollama-Lock, Evict-Models, Force-Purge, Logging, Gaming-Override) verlangen jetzt wie /admin/* den X-Admin-Token-Header — vorher waren sie offen für jeden im LAN. Die Status-Seite GET /status/gpu/html verlangt aus demselben Grund jetzt ?token=<admin-token>, statt den Token unauthentifiziert an jeden Besucher auszuliefern.

v2.5.0 — Ollama-Lock für exklusive GPU-Nutzung

24. Juli 2026
  • Ollama-Lock: POST /maintenance/ollama-lock sperrt gezielt nur den Zugriff auf lokale Ollama-Modelle und entlädt sie sofort aus dem VRAM — gedacht für den Fall, dass beide GPUs kurzzeitig exklusiv für ComfyUI gebraucht werden. POST /maintenance/ollama-unlock hebt die Sperre wieder auf.
  • Fallback bleibt aktiv: Im Unterschied zum bestehenden Stop-All-Modus werden Clients mit Frontier-Fallback (fallback.yaml) bei aktivem Lock weiterhin bedient — nur die lokale GPU bleibt frei.
  • Persistiert: Der Zustand wird in config/ollama_lock.yaml gespeichert und übersteht damit einen Neustart des Proxys.
  • Dashboard: Neuer Schalter unter Admin → Settings → „🔒 Ollama-Lock".

v2.4.0 — Ollama-Fallback auf Frontier-Modelle

22. Juli 2026
  • Auto-Failover: Ist der zuständige Ollama-Upstream nicht erreichbar, leitet /v1/chat/completions automatisch auf ein konfiguriertes Frontier-Modell um (fallback.yaml) — nur für Clients mit "Allow Frontier LLMs".
  • Admin UI: Neuer „Fallback"-Tab im Dashboard zur Modell-Zuordnung (lokal → Frontier), inkl. Live-Health-Status pro Upstream.
  • "*"-Catchall: Ein "*"-Key im Mapping wirkt als Fallback für jedes Modell ohne eigenen Eintrag.
  • Bugfixes: Frontier-Modell-Liste blieb in der Admin-UI leer, wenn Ollama down war (entkoppelte Fetches); Dropdown statt Freitext-Datalist für robusteres Modell-Mapping.

v2.3.0 — Parallele GPU-Nutzung & Maintenance-Tools

29. Juni 2026
  • Round-Robin Routing: Wenn beide GPUs frei sind, verteilt der Proxy parallele Requests automatisch auf GPU 0 (RTX 3080) und GPU 1 (RTX 3060) — echte Parallelität statt sequentieller Warteschlange.
  • Stop-All Modus: POST /maintenance/stop-all blockiert sofort alle Inference-Requests (HTTP 503) und killt laufende Prozesse. POST /maintenance/resume hebt den Modus wieder auf.
  • Force-Purge: POST /maintenance/force-purge — zweistufiger Hard-Reset: erst soft evict via keep_alive: 0, dann SIGKILL auf alle llama-server Prozesse.
  • GPU-Status-Seite: GET /status/gpu/html — Live-Übersicht welches Modell auf welcher GPU läuft, welcher Client aktiv ist, VRAM/Load/Temp. Auto-Refresh alle 5s.
  • Upstream-Tracking: Aktive Requests werden jetzt mit GPU-Index gespeichert — sichtbar in GET /status/gpu.
  • Bugfix GGML_VK: GGML_VK_VISIBLE_DEVICES wurde von Ollama intern gesetzt und übersteuerte CUDA_VISIBLE_DEVICES — Fix via systemd Drop-in.

v2.2.0 — Admin UI & Frontier LLMs

19. Juni 2026
  • Admin UI: Clients, Limits und Block-Regeln können nun direkt über das Dashboard gesteuert werden.
  • Frontier Proxy: Native Unterstützung für externe APIs (OpenAI-kompatibel, z. B. Gemini, OpenRouter), die direkt transparent durch llmproxy durchgeschleift werden.
  • Model-Picker: Erlaubte Modelle pro Client lassen sich nun komfortabel per Checkbox auswählen.
  • Open-Source Release: Das Projekt wurde bereinigt und generalisiert (Lizenzen, Docs, generische Hostnames).

v2.1.0 — Dual-Ollama Architektur & Smart Routing

07. Juni 2026
  • Asymmetrisches Multi-GPU: Umstellung auf 2x isolierte Ollama-Instanzen (RTX 3080 auf Port 11434, RTX 3060 auf Port 11438).
  • GPU-Aware Routing: `routing.yaml` unterstützt jetzt target_gpu. Bei Auslastung von GPU 0 wird automatisch auf GPU 1 ausgewichen (Load-Shedding).
  • Kritischer Bugfix: Idle Eviction nutzt jetzt keep_alive: 0 statt DELETE /api/delete, womit Modelle nicht mehr versehentlich von der Festplatte gelöscht werden!
  • Dashboard: Diese neue Update/Changelog-Seite hinzugefügt.
